Launcher Electronics

Interim assumptions and physical onboarding

The interim electrical & software write-up captured the intended launcher architecture before full robot bring-up. At that stage, several choices—especially latch release and tension sensing—were justified from datasheets and mechanical intent rather than from integrated testing. First electronics onboarding on hardware quickly surfaced coupling issues (solenoid release versus draw depth, feeder timing, and torque observability) that the interim document could not predict. The sections below follow a hybrid, iteration-first order: a short evolution strip and log table for scanning, then deeper component evidence, bench data, and firmware narrative.

Design requirements

Force / torque awareness

The electronics must resolve motor torque well enough to infer band tension during the draw stroke so preload can be repeated shot to shot.

Measurement resolution

The acquisition path targets 12-bit effective resolution with headroom to approximately 40 N·m peak so spikes during latch or snag events do not saturate silently.

Latch state (evolved)

Interim design targeted a solenoid lock for fast release; bring-up showed limits at larger draws. The final requirement keeps explicit lock detection while using a servo for repeatable release—firmware must never fire while the band is incorrectly coupled.

Controlled release

A dedicated servo disengages the lock on command with timing compatible with the fire sequence and feeder motion.

Smooth energy delivery

Torque and speed profiles should ramp so the carriage does not shock the band, bearings, or dart interface.

Shot policy

The first dart from a preloaded state follows a different branch than later darts that depend on feeder motion; both must be verified.

Safe tuning

When calibrating travel limits, the operator must be able to stop motion immediately if the carriage overshoots the load window.

First electronics onboarding (independent launcher)

The first firmware path brought up only the launcher motor, the solenoid lock, and a remote controller link. This was deliberately not merged with feeder tasks so mechanical could swap elastic bands, verify rail travel, and exercise fire timing without debugging indexer states. Independent code reduced the failure domain while the latch and draw kinematics were still changing week to week.

Optical endstop

Launcher rail datum

Optical switch — tap to expand role and interface

An optical endstop on the launcher rail gives a repeatable electrical datum for carriage position. Firmware uses this line together with motor position/torque to decide when the shuttle is at the load/fire region aligned with feeder hooks, and to sanity-check motion during multi-shot sequences. The sensor output is treated as a debounced digital input to the MCU (same family as the feeder indexer endstops; see the feeder electronics section for the optical vs. mechanical comparison).

Solenoid lock

The solenoid was attractive for fast, single-action release: energise to retract the bolt, de-energise to reset. Test evidence — solenoid release bench

This setup isolated the solenoid driver, mechanical latch, and launcher carriage position from the rest of the robot so failures could be attributed to release margin—not feeder indexing. Observed behaviour: beyond roughly 0.2 m pullback (with the band configurations tested), release became inconsistent; increasing drive voltage did not restore margin in a way that felt safe for competition use. That outcome directly motivated migrating dart release to a servo-actuated latch with deterministic travel.

Solenoid supply vs. draw depth at release

A bench PSU swept the solenoid rail while the launcher was positioned to representative pullback distances. The goal was to see whether higher coil voltage recovered reliable release at deep draws. The trend supported the pivot: the mechanism behaved as a binary plunger with limited controllable overlap against growing band load.

Design evolution: solenoid → servo release

Why a solenoid first: fastest path to “fire” in software, minimal PWM choreography, and easy bench wiring for mechanical band experiments.

Weaknesses observed: (i) binary stroke with little mid-travel authority against rising band tension; (ii) inrush and holding current spikes on the supply and FETs when chasing margin; (iii) thermal and repeatability concerns under rapid shot strings; (iv) difficulty mapping a clean “armed” window in firmware when mechanical lash and draw depth co-vary.

Why servo release won: bounded travel, programmable speed, and easier integration with the state machine (wait for settle, verify lock sense, then fire). The electronics cost is an extra PWM channel and mechanical packaging—not a fragile compromise on release physics at the edge of solenoid spec.

Torque / tension observation

Draw-stroke torque for closed-loop preload is observed through the 12-bit instrumentation path—primarily launcher motor telemetry after the load-cell concept was retired—scaled in firmware to represent band tension consistently shot to shot.

Launcher PCB / module

CAN to the DM-J8009, lock drivers, release servo interface, torque-conditioning / ADC channels, and connectors to the wire-management harness. Lock detection remains debounced on a digital input whether a given build used solenoid or servo release.

Implementation

Code evolution timeline

  1. Single-shot launcher firmware — independent task handling preload, draw, and release for mechanical band testing (remote-driven).
  2. Load-cell path retired — tension inferred from actuator torque / draw stroke to reduce harness complexity and align sensing with the same element doing the work.
  3. Feeder integration — additional signals: launcher carriage relative to optical_endstop, rotary indexer position, and delays for servo settling after hooks move.
  4. General state machine — unified branches for first-shot-preloaded vs feeder-fed shots, with explicit guards on lock sense and torque targets.
  5. Tuning iteration — compile-time C directives to isolate feeder states and expose parameters to live expressions during debug sessions.

Load cell → launcher-motor tension

Early sketches used a parallel load channel for “true” tension. Bring-up showed calibration drift and routing fragility for little benefit once the Damiao torque telemetry proved monotonic under static pulls. Firmware was refactored to track the same draw torque budget through the motor stack, which also simplified correlating logs with CAN traces during fire tuning.

Feeder integration signals

Integrated firing needed agreement between where the launcher thinks it is (relative to the optical datum), where the feeder rotary stage is after indexing, and how long servos take to settle after a hook command. Those inputs collapse into explicit states: advance-to-datum, couple band, draw-to-torque, release, and safe re-park—each with timeouts derived from tuning runs.

Compile-time directives and live tuning

Late iteration used #ifdef / #define switches to freeze risky paths while experimenting—e.g. exercising only feeder transitions, or only torque-guided draw—with the same binary. Selected gains, delays, and torque thresholds were then adjusted through live expressions in the IDE where supported, avoiding constant reflash for minor parameter nudges during bench sessions.

On boot the firmware assumes a parked pose near the bottom of the rail, close to the motor, to minimise unexpected potential energy in the band. A fire request first commands forward motion until lock detected is true. If the barrel already contains a preloaded dart, the sequence retracts while monitoring torque until the release threshold is met, then commands the release servo and completes the shot. For subsequent rounds, the launcher cooperates with the feeder: advance to the optical datum, allow load, clear hooks, then repeat the torque-guided draw and release.

Torque-based control deliberately ramps effort so rotational power couples smoothly into the elastic element, improving repeatability when dart mass or band age changes, and giving a logged variable that can be correlated with downrange performance during experiments.

Testing

Solenoid bench (characterisation)

PSU sweep and pullback trials documented above; conclusions fed directly into the servo release pivot and into minimum acceptable margins for fire gating.

Torque path and saturation

Static pulls against a blocked carriage verify monotonic ADC output against applied load and confirm the chain does not clip below the maximum expected draw event.

Lock detection

The sense line is toggled through manual latch / release cycles while logging debounced state to ensure no fire command is accepted when detection disagrees with mechanical reality.

Preloaded first shot

With a dart staged only by the launcher, the branch that skips feeder choreography is exercised and torque traces are checked for the expected single draw peak.

Feeder-coupled follow-on shots

Multi-shot strings validate transitions from feeder endstop through hook engagement and back to torque-guided fire without state leakage between cycles.

Tuning and e-stop

During limit calibration, intentional overshoot attempts are interrupted by the handheld remote to confirm motors de-energise and control hands off safely before parameters are written back.
