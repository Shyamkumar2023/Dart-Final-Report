Launcher Electronics

Design Requirements

Reliable launcher operation depends on four core functional elements: measuring force to determine firing force, detecting latch engagement to confirm pull-back, actuating the release mechanism to fire, and driving the linear rail with a motor to perform the pull-back motion.

What was required

The first bring-up goal was to exercise the launcher alone: prove the carriage could draw elastic preload under motor control, that a latch could release on command, and that an operator could stop the rig quickly—without debugging feeder indexing or multi-subsystem timing. That deliberately shrank the failure domain while rail travel, band sets, and latch geometry were still changing weekly.

Interim reasoning (pre–full onboarding) favoured a solenoid for release because it offered the shortest path to a software-triggered “fire,” minimal PWM choreography, and straightforward bench wiring next to a relay for clean energisation of the coil. A remote controller was included for manual draw/release and emergency stop authority during mechanical experiments. Those choices were plausible from datasheets and intent; whether release stayed reliable at depth under real band load was left to bench testing—documented in the testing subsection below.

What testing was done

Test evidence — solenoid release bench

This setup isolated the solenoid driver, mechanical latch, and launcher carriage position from the rest of the robot so failures could be attributed to release margin—not feeder indexing. Observed behaviour: beyond roughly 0.2 m pullback (with the band configurations tested), release became inconsistent; increasing drive voltage did not restore margin in a way that felt safe for competition use. That outcome directly motivated migrating dart release to a servo-actuated latch with deterministic travel.

Solenoid supply vs. draw depth at release

Solenoid bench characterisation from the isolated launcher bring-up: PSU sweep and pullback trials; conclusions fed directly into the servo release pivot and minimum acceptable margins for fire gating.

A bench PSU swept the solenoid rail while the launcher was positioned to representative pullback distances. The goal was to see whether higher coil voltage recovered reliable release at deep draws. The trend supported the pivot: the mechanism behaved as a binary plunger with limited controllable overlap against growing band load.

Load cell removed from the V0 path

The interim (V0) architecture assumed explicit tension / firing-force sensing—commonly a load-cell path alongside the launcher. That path was removed in favour of launcher motor torque and CAN telemetry (see the evolution strip: “load-cell path retired in favour of launcher motor torque telemetry”). The same “measure force” requirement from the design block is still met, but without a separate strain-gauge channel on the rail.

Force reading

For force-related conclusions, the testing already described under V1—Test evidence — solenoid release bench, the pullback / carriage-position context, and the solenoid supply vs. draw depth sweep, table, and interpretation—can be reused for force reading: draw depth, supply margin, and release outcome bracket preload and release reliability together with motor torque, without relying on a load cell.

Extra signals

The integrated stack needs additional inputs: distance from the optical sensor, position of the feeder motor, and delays for servos so datum alignment, indexing, and fire sequencing stay coherent across both subsystems.

Software integration

More code was written to integrate feeder and launcher firmware that had been written independently: shared state, hand-offs, and coordination so the combined behaviour matches the full-robot electrical and mechanical intent.

V4 is additional code written to aid tuning—supporting faster iteration when calibrating parameters and checking behaviour on the bench. Bring-up bench evidence for the solenoid rail remains under V1.
